# Future Project 6 Input Interface

[SYNTHETIC — FOR DEMONSTRATION ONLY]

> Human Review Required: AI-generated outputs are decision-support artifacts only. A qualified engineer owns final review and approval.

## Problem

Project 5 may eventually need structured LED model inputs generated by Project 6. The interface must preserve engineering review boundaries so Project 5 remains a feasibility screening tool, not a datasheet validation or design approval tool.

## Engineering Context

Project 6 is now framed as the upstream LED Datasheet-to-Model Extractor. Its deterministic evidence currently lives in `projects/wcca-prep-tool/datasheet-plot-digitizer` as LED Datasheet Curve Studio. Its future integration role is to transform sanitized or synthetic datasheet-style information into reviewed LED model CSV or JSON records.

Project 5 should eventually consume only reviewed LED model CSV or JSON outputs from Project 6. Project 5 must not consume raw datasheet extraction directly, and it must not parse PDF datasheets, validate datasheet correctness, or infer final engineering acceptance from extracted values.

Project 5 performs feasibility screening using structured, reviewed inputs. It does not approve engineering decisions, release designs, validate requirements, validate datasheet correctness, or replace review by a qualified engineer.

## Workflow

1. Project 6 extracts LED model candidates from synthetic or sanitized datasheet-style source material.
2. A qualified reviewer checks the extracted model values, source traceability, assumptions, and engineering notes.
3. Project 6 exports reviewed LED model records as CSV or JSON.
4. A future Project 5 adapter maps reviewed Project 6 records into the Project 5 lighting case input format.
5. Project 5 runs deterministic feasibility screening on the structured, reviewed input values.
6. A qualified engineer reviews Project 5 outputs before any public use or engineering interpretation.

## Inputs

Future Project 6 inputs to Project 5 must be reviewed model records, not raw extraction output. The current extractor package demonstrates CSV, JSON metadata, lookup files, and overlay-review evidence, but it does not yet define the final Project 5 adapter schema.

Any Project 6 input row or object must include:

- `review_status`
- `extraction_confidence`
- `source_page`
- `source_section`
- `assumptions`
- `engineering_notes`

Project 5 should warn or reject any Project 6 row that is not marked reviewed for synthetic or demo use. The expected gate is `review_status` with an explicit reviewed state, such as `reviewed_demo` or another controlled value defined by the future adapter.

## Outputs

The future adapter concept is:

```text
Project 6 reviewed_led_model.json/csv -> Project 5 lighting case input format
```

The adapter output should remain a normal Project 5 lighting case input file with reviewed, structured values. It should not include raw datasheet text, proprietary source details, internal document identifiers, supplier part numbers, customer identifiers, program names, or uncontrolled extraction notes.

## Risks And Mitigations

- Risk: Raw datasheet extraction could be treated as validated engineering input. Mitigation: Project 5 should accept only reviewed Project 6 CSV or JSON records.
- Risk: A Project 5 result could be misread as approval of Project 6 extraction quality. Mitigation: Project 5 documentation states that it does not validate datasheet correctness.
- Risk: Missing source traceability could hide extraction assumptions. Mitigation: each Project 6 row must include review status, confidence, source page, source section, assumptions, and engineering notes.
- Risk: Future adapter logic could create a hard dependency on Project 6. Mitigation: keep Project 6 integration as an optional adapter that emits the existing Project 5 input format.
